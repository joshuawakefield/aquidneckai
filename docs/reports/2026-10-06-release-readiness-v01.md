## Rollback gates (not executed)

For **code-only rollback**, retain the actual last verified artifact plus immutable commit/build identity and compatible server configuration before deployment; test against the intended schema. Historical `b34b14e` is a reference, not a guaranteed available or currently compatible rollback image. If auth leaks, publication correctness regresses, key routes fail or the new build cannot operate, use the separately authorized host rollback to the known compatible artifact and verify the same route/content/health matrix. Do not force/reset the shared branch. A Git revert prepares another reviewed build; it does not roll back hosting, configuration or data. Rebuilding an old SHA against unpinned container/OS packages is not identical to restoring its retained artifact.

For **committed data/schema changes**, use AQ-002's private snapshot, restore rehearsal, prior function/ACL definitions and application-compatibility evidence. Define acceptable loss/downtime and an authorized operator before the change. Transaction ROLLBACK only undoes an uncommitted transaction. Never drop columns/tables or replay old migrations as a generic rollback. Restoring old state can discard reviews and resurrect paid claims/leases; reconcile later writes and uncertain paid outcomes, with separately authorized worker quiescence. No code rollback can retract an external publication, sent message or paid inference. DNS rollback likewise restores only reviewed web records, not database state, and can remain mixed during propagation.
